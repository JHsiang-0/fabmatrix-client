# FabMatrix 版本与路线地图

本文是前端文档的版本解释入口。它解决三个容易混淆的概念：产品发布版本、API 路径版本、Kiro 开发阶段编号。

## 1. 当前发布基线

| 项目 | 当前结论 |
| --- | --- |
| 产品名称 | 嘉东三维联动3D打印机实时控制系统 / FabMatrix |
| 产品版本 | `1.0.0` 准正式版 |
| 候选标识 | `v1.0.0-rc.1` |
| 发布形态 | Windows Local Edition：一个本地服务端 + 多个 Electron 客户端 |
| 默认服务端口 | `28081`；HTTP 与 WebSocket 使用同一后端端口 |
| 数据形态 | SQLite/本地文件存储；不把 MySQL、Redis、RustFS 作为本版本安装前提 |
| 当前发布门禁 | `.kiro/specs/farm-v1-release-readiness/` 和 `npm run release:gate` |

1.0.0 准正式版的目标是完成可安装、可启动、可初始化、可登录、可联机和核心业务可回归的本地版。真实 Windows 安装/升级/卸载、真实打印机和长时间网络稳定性仍需在实际环境完成验收后，才能标记为正式发布。

2026-10-08 稳定性整改归属 R100-14：隔离退出/重登前后的客户端身份恢复请求，修复旧身份覆盖、旧失败清空新会话和无登录态恢复请求错误复用；请求层共享会话代次，覆盖同 Token 重登的旧 401 与变更请求去重。沿用现有认证接口及 `1.0.0` 版本，验证结果记录在发布任务清单中。

2026-10-08 R100-15 增加已登记打印机 DHCP 地址恢复的管理员手动同步入口：前端展示后台扫描范围、进行中任务和逐项结果，完成后刷新列表，普通刷新保持读取列表。自动发现及 MAC/协议核对由后端负责；真实关机、换 IP、再开机的现场验收仍需部署后执行，产品版本继续使用 `1.0.0`。

2026-10-08 R100-16 增加打印历史 Excel/PDF 导出：ADMIN 可导出全部或按创建人筛选，OPERATOR 仅本人任务。前端明确使用最近一次成功查询条件并导出全部分页，后端负责权限、限额、名称快照和报表生成；公共文件生成能力可由其他业务导出复用。产品版本继续为 `1.0.0`，现场真实数据导出及安装/升级验收另行记录。

2026-10-08 R100-16 追加导出体验调整：弹窗打开时复制列表条件，随后支持独立编辑和直接导出，提供重置全历史/恢复列表条件，保持列表结果不变；设备名称建议优先缓存、缺失时限100条，历史设备仍可输入ID。Excel 默认明细第一张、统计第二张，Mock/下载读回验证完整13字段；PDF表格由配套后端调整。当前需求以本轮实现与发布任务追加证据为准，先前验收作为历史记录保留。

2026-10-08 R100-16-UI 独立维护导出弹窗布局：使用默认 TDesign 顶部标签、响应式双列、整行日期范围、默认 Typography/Form help 和原生页脚，移除导出专用 CSS。辅助按钮改为“清空筛选”和“使用列表筛选”，通过 Tooltip 说明全部终态/清空条件与恢复最近成功列表条件的区别。375px 日期面板通过官方 Popup 属性和通用布局工具在内层横向滚动。产品版本、接口、资源归属和后端报表保持原基线；验证及独立客户端产物在发布任务中记录。

## 2. 版本术语映射

2026-11-05 云端组织与农场管理首期归入独立云接入功能，页面 `/cloud/manage` 与 Cloud V17 配套，沿用客户端 `1.0.0` 版本及现有岗位体系。资料、概览、成员授权、网关及审计 GUI 的范围与验收见 [云端管理](CLOUD_MANAGEMENT.md)。云端服务和应用安装升级分别安排。

同日补齐局域网主界面的“云端平台”侧栏和顶部管理入口，支持独立云登录后返回目标管理页及返回局域网主界面，沿用上述云接入功能归属。

| 术语 | 实际含义 | 处理方式 |
| --- | --- | --- |
| `1.0.0` | 当前对外产品版本 | 所有前端、Electron、服务端和安装器对外统一使用 |
| `/api/v1` | HTTP API 的兼容路径 | 保持不变，不改成 `/api/1.0.0` |
| v1 | 最初的业务/协议基础能力和历史验收阶段 | 作为历史基础保留 |
| v2 | 手动优先、Local Edition、任务可读性和文件管理等功能阶段 | 作为功能实现来源保留；是否进入 1.0.0 由 R100 门禁决定 |
| v3 | 后台自动派单及更高风险批量派发路线 | 1.0.0 隐藏或不开放，后续单独发布 |

因此，Kiro 目录名和任务编号中的 v1/v2/v3 不应直接替换成产品版本号，也不能据此判断某个接口是否属于当前发布范围。

## 3. Kiro 规格归属

| 规格 | 状态 | 归属 |
| --- | --- | --- |
| `farm-v1-release-readiness` | 当前发布门禁 | 1.0.0 准正式版；R100 任务以真实验证结果为准 |
| `farm-ui-v2` | 历史功能基线 | 手动上传、文件库、任务中心、权限和看板等功能来源；不等于“发布 v2” |
| `farm-v3-batch-dispatch` | 后续规划 | 后台自动派单、批量执行和恢复模型；不进入 1.0.0 发布门禁 |
| `farm-dashboard-dynamic-layout` | 功能规格/验收记录 | 看板动态行列和过道编辑，按 R100 范围决定是否随版本交付 |
| `farm-task-center-readability` | 功能规格/验收记录 | 任务可读名称、快照和历史显示 |
| `farm-ardot-tdesign-prototype` | 规划中的原型规格 | 使用 Ardot 与 TDesign for web 建立可评审前端原型；评审通过后再进入 Vue 编码 |
| `printer-*` | 协议、监控和 WebSocket 规格 | 以真实设备联调状态为准 |
| `farm-ui-remediation`、`farm-ui-selective-integration` | 历史整改/合并记录 | 只作为变更依据和回归证据 |

## 4. 文档权威顺序

出现冲突时按以下顺序判断：

1. 当前代码、实际配置和自动化验证结果；
2. `farm-v1-release-readiness` 的发布范围与验收记录；
3. `API_HANDOFF.md` 的接口契约；
4. 具体功能 Kiro 的 requirements/design/tasks；
5. 根目录 TODO 和历史说明。

根目录 TODO 允许保留历史任务，但不得用来覆盖 R100 的发布范围。

## 5. 当前未纳入 1.0.0 的能力

- 后台无人确认的自动派单。
- 依赖 MySQL、Redis、RustFS 的 Server Edition 安装交付。
- 未完成真实设备验证的协议或控制能力。
- 未通过安装器、升级、卸载和数据保留验收的发布结论。

## 6. 新任务维护规则

- 新任务先注明产品版本和 Kiro 规格归属，再写实现任务。
- Ardot/TDesign 原型任务必须区分“原型完成”和“Vue 编码完成”，不得只因组件已拖入画布就标记前端功能完成。
- 产品版本统一写 `1.0.0`；历史阶段可写“v2 功能基线”，不要写成“产品 v2 发布”。
- 涉及接口时保留 `/api/v1`，并说明这是 API 路径而非产品版本。
- 完成任务后同步对应 `tasks.md`、接口契约、验证记录和本索引；不要批量改名历史目录。
