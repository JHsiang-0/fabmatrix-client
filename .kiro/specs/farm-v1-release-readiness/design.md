# FabMatrix 1.0.0 准正式版发布整改设计

版本：1.0.0
对应需求：`.kiro/specs/farm-v1-release-readiness/requirements.md`
任务标识：R100
状态：代码整改基本完成；R100-07 与真实环境验收待完成

## 1. 设计原则

- 以 Windows Local Server + Electron 客户端为唯一发布基线。
- 先消除安全和真实设备控制阻断，再处理数据完整性和发布工程。
- 一个子任务只允许一个代码写入者，并独立测试、提交和验收。
- 后端是权限、状态机和设备动作的最终边界；前端隐藏不能替代后端约束。
- 安装成功、服务启动成功和业务健康是三个不同状态，必须分别验证。

## 2. 版本与产物设计

统一数字版本为 `1.0.0`，准正式属性通过发布渠道表达：

```text
产品显示       v1.0.0 准正式版
客户端版本     1.0.0
后端版本       1.0.0
Windows 版本   1.0.0.0
候选标签       v1.0.0-rc.1
正式标签       v1.0.0
```

构建过程应从一个受版本控制的版本源校验所有子项目配置；任意组件版本不一致时发布检查直接失败。

## 3. 首次初始化设计

安装器生成高熵、短期有效、单次使用的 bootstrap token，并保存至仅管理员和服务账户可读取的位置。服务端初始化接口同时验证：

```text
用户数为 0
AND setup 状态未完成
AND bootstrap token 匹配
AND token 未过期、未使用
```

首次管理员创建和 setup 状态落库必须处于同一事务。成功后删除或作废本地 token。托盘只能提供初始化入口或复制地址，不能长期显示明文 token。

## 4. 会话设计

用户表增加或复用会话版本字段。JWT 携带用户 ID、角色、过期时间和会话版本。认证过滤器读取当前用户的 enabled、role 和版本，不再只信任 Token 中的角色。

改密、禁用、角色变化时递增版本。WebSocket 保存认证上下文，在令牌过期或定期检查失败时主动关闭连接。最后一个启用 ADMIN 的降级和停用操作在事务内拒绝。

## 5. 设备控制设计

所有打印机写操作进入同一协调器：

```text
校验权限和状态
→ 获取可续租 fencing lock
→ CAS 写入命令处理中状态
→ 使用 commandId 下发设备命令
→ 保存设备回执和最终状态
→ 释放锁并广播
```

外部设备 I/O 不依赖数据库事务回滚。设备动作结果不确定时进入 `RECONCILING`，由监控和人工核对恢复，不允许直接伪造成功或回退到空闲。

## 6. 文件与存储设计

上传使用临时文件和原子落盘：容量预检、写入临时文件、校验、原子移动、提交数据库。删除使用可恢复状态或事务后清理，避免先永久删除对象。缩略图按真实 key 和 MIME 返回。

日志采用按日期与大小轮转，并设置保留天数和总容量。数据目录、日志目录和服务状态目录都必须由完全卸载流程显式识别。

## 7. 安装器设计

安装器完成服务注册和启动后，轮询：

```text
TCP 28081 可连接
→ GET /actuator/health 为 UP
→ 运行版本为 1.0.0
```

任一步失败均不得写入成功标记。托盘读取的是服务实际确认后的端口元数据。卸载器先停止服务和托盘，再处理运行时文件；数据是否删除由用户明确选择。

## 8. Electron 设计

生产环境只允许应用自身 `file://` 页面或冻结的开发地址。主窗口导航、重定向、新窗口和 IPC 均实施来源校验。CSP 覆盖脚本、连接、图片和样式来源。测试开关只在 `!app.isPackaged` 时允许。

正式包和 Mock 包使用不同的 appId、productName、图标或明显标识及输出目录，避免误发和覆盖。

## 9. 发布流水线

候选发布顺序固定为：

```text
工作区与版本检查
→ 前端单测/lint/build
→ 后端 test/verify
→ 安装器契约测试
→ 打包正式客户端和服务器
→ 安装后健康与初始化冒烟
→ REST/WS/上传/任务冒烟
→ 升级与两种卸载验证
→ 生成校验和与验收记录
```

任何步骤失败都不得生成可对外交付的正式目录。

## 10. 实施边界

R100 是一个发布整改总任务，内部子任务必须按 `tasks.md` 顺序实施。涉及后端契约、数据库迁移和设备控制时，前后端分别提交并记录依赖提交；不得在一个不可审查的大提交中一次完成全部整改。
